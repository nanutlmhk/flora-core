# เอกสารขอบเขตงานโครงการ
## ระบบจัดการ PDF Report จาก Innovian เพื่อเตรียมส่งต่อเข้า EPHIS

เอกสารฉบับนี้จัดทำขึ้นเพื่อใช้สรุป `ขอบเขตงาน (Project Scope)` สำหรับส่งให้ลูกค้าใช้พิจารณาแนวทางดำเนินโครงการก่อนการสรุปราคาและแผนดำเนินงานอย่างเป็นทางการ

เอกสารนี้มีวัตถุประสงค์เพื่อให้ทุกฝ่ายเข้าใจตรงกันในเรื่อง

- เป้าหมายของโครงการ
- ขอบเขตงานที่รวมอยู่ในโครงการ
- สิ่งที่จะส่งมอบ
- ข้อสมมติฐานและเงื่อนไขสำคัญ
- สิ่งที่อยู่นอกขอบเขต

เอกสารนี้ยังไม่ใช่สัญญาว่าจ้างหรือใบเสนอราคา แต่ใช้เป็นเอกสารอ้างอิงเพื่อยืนยัน `scope` ของงานก่อนเริ่มดำเนินการ

---

## 1. หลักการและที่มาของโครงการ

ปัจจุบันการจัดการไฟล์ `PDF report` ที่ export ออกจาก `Innovian` เพื่อเตรียมส่งต่อเข้าสู่ workflow ของโรงพยาบาลหรือ `EPHIS` ยังมีขั้นตอนที่ต้องอาศัยการตรวจสอบและจัดการด้วยมือในหลายส่วน เช่น

- ชื่อไฟล์จากต้นทางไม่เหมาะสำหรับการจัดเก็บปลายทาง
- ผู้ป่วยรายเดียวกันอาจมีมากกว่า 1 case ในวันเดียวกัน
- การใช้ชื่อไฟล์แบบ `HN.pdf` มีความเสี่ยงต่อการถูกเขียนทับ
- มี PDF หลายประเภทที่เกี่ยวข้องกับ encounter เดียวกัน
- ต้องใช้เวลาในการตรวจสอบ เปลี่ยนชื่อ รวมไฟล์ และส่งไฟล์ด้วยมือ
- มีความเสี่ยงต่อการจัดเก็บผิดคนหรือผิด encounter

ดังนั้นโครงการนี้มีเป้าหมายเพื่อพัฒนาระบบช่วยจัดการ `PDF management workflow` ให้มีความถูกต้อง ปลอดภัย และลดภาระงานของผู้ใช้งาน

---

## 2. วัตถุประสงค์ของโครงการ

โครงการนี้มีวัตถุประสงค์เพื่อพัฒนาระบบหรือเครื่องมือที่สามารถ

- รับไฟล์ PDF ที่ export จาก `Innovian`
- ตรวจสอบและเปรียบเทียบข้อมูล case ประจำวันกับไฟล์ PDF ที่มีอยู่
- อ่านข้อมูลจากเนื้อหา PDF เพื่อช่วยระบุตัวผู้ป่วยและบริบทของ case
- เปลี่ยนชื่อไฟล์ให้เป็นรูปแบบที่ปลอดภัยกว่าและสอดคล้องกับ workflow ปลายทาง
- รวมไฟล์ PDF ที่เกี่ยวข้องกับ encounter เดียวกันตามกติกาที่กำหนด
- จัดเก็บไฟล์ต้นฉบับและไฟล์ที่ผ่านการประมวลผลอย่างเป็นระบบ
- ส่งไฟล์ PDF ปลายทางตาม schedule ที่กำหนดโดยอัตโนมัติ
- สร้าง log และข้อมูลสำหรับตรวจสอบย้อนหลังได้

---

## 3. ขอบเขตงานหลัก

ขอบเขตงานในระยะนี้ครอบคลุมงานหลักดังต่อไปนี้

### 3.1 การรับและตรวจสอบไฟล์ PDF ต้นทาง

- ตรวจจับไฟล์ PDF จาก source folder ที่กำหนด
- รองรับการประมวลผลแบบ batch
- คัดแยกเฉพาะไฟล์ที่เกี่ยวข้องกับ workflow นี้
- รองรับการทำงานซ้ำอย่างปลอดภัยในกรณี rerun

### 3.2 การวิเคราะห์ข้อมูลจาก PDF

- อ่านข้อความจากไฟล์ PDF
- ดึงข้อมูลสำคัญที่ใช้ระบุผู้ป่วยหรือ case เช่น `HN`, วันเวลา, ประเภท report หรือ field อื่นที่มีอยู่จริงในเอกสาร
- วิเคราะห์ว่า metadata ใดมีความเสถียรพอสำหรับใช้ในการตั้งชื่อไฟล์และ grouping

### 3.3 การเปรียบเทียบข้อมูลรายวัน

- เปรียบเทียบรายการ case จากต้นทางกับไฟล์ PDF ที่มีอยู่ในปลายทาง
- ระบุกรณีที่พบ เช่น
  - มี case แต่ยังไม่มี PDF
  - มี PDF แต่ไม่ตรงกับ case ที่คาดไว้
  - มีหลาย case ของ HN เดียวกันในวันเดียวกัน
  - มีความเสี่ยงที่ไฟล์จะถูกเขียนทับหรือแทนกัน

### 3.4 การตั้งชื่อไฟล์แบบ case-aware

- พัฒนากติกาการตั้งชื่อไฟล์ใหม่แทนการใช้รูปแบบ `HN.pdf`
- รองรับชื่อไฟล์ที่มีข้อมูลระดับ case หรือ encounter เช่น
  - `HN_admitdate_time.pdf`
  - หรือรูปแบบอื่นที่ตกลงร่วมกันภายหลัง
- ลดความเสี่ยงของการแทนที่ไฟล์ในกรณีที่ผู้ป่วยมีหลาย case ในวันเดียวกัน

### 3.5 การจัดกลุ่มและรวมไฟล์ PDF

- จัดกลุ่มไฟล์ที่เกี่ยวข้องกับ encounter เดียวกัน
- รวมไฟล์ PDF ตามลำดับและเงื่อนไขที่กำหนด
- หากระบบไม่สามารถตัดสินใจได้อย่างปลอดภัย ต้องสามารถ flag เพื่อให้ review ด้วยมือได้

### 3.6 การส่งไฟล์ปลายทางอัตโนมัติ

- รองรับการประมวลผลและส่งไฟล์อัตโนมัติแบบ daily schedule
- แนวทางปัจจุบันคือทำงานหลังเที่ยงคืน
- รองรับการจัดเก็บไฟล์ final ไปยัง destination folder ที่กำหนด

### 3.7 การเก็บ archive และ log

- เก็บไฟล์ต้นฉบับก่อนประมวลผล
- เก็บ log การทำงานของแต่ละรอบ
- สามารถตรวจสอบย้อนหลังได้ว่าไฟล์ใดถูกอ่าน เปลี่ยนชื่อ รวม หรือส่งแล้ว

### 3.8 เอกสารและ handover

- จัดทำเอกสารการใช้งานเบื้องต้น
- อธิบาย folder flow
- อธิบายวิธีตรวจสอบกรณี error หรือ ambiguous case
- ส่งมอบแนวทางใช้งานให้ทีมที่เกี่ยวข้อง

## 4. สิ่งที่จะส่งมอบ (Deliverables)

เมื่อโครงการเสร็จสิ้นตามขอบเขตที่ตกลง ลูกค้าจะได้รับสิ่งส่งมอบหลักดังนี้

### 4.1 โปรแกรมหรือ utility สำหรับจัดการ PDF

ระบบหรือ utility สำหรับ Windows ที่สามารถดำเนิน workflow ตามที่กำหนดได้ เช่น

- scan source folder
- อ่านข้อมูลจาก PDF
- เปลี่ยนชื่อไฟล์
- จัดกลุ่ม / merge
- copy หรือ move ไปยัง destination
- เก็บ archive และ log

### 4.2 กติกาการตั้งชื่อและจัดกลุ่มไฟล์

logic ที่ใช้สำหรับ

- แยก encounter
- ตั้งชื่อไฟล์ final
- merge report ที่เกี่ยวข้อง
- block กรณีที่มีความกำกวม

### 4.3 Daily comparison output

ผลลัพธ์หรือรายงานสำหรับใช้ตรวจสอบความครบถ้วนของไฟล์ในแต่ละวัน เช่น

- missing PDF
- duplicate same-day case
- overwrite risk
- unmatched file

### 4.4 Automated processing workflow

workflow ที่พร้อมใช้งานสำหรับประมวลผลแบบ scheduled run ตามช่วงเวลาที่กำหนด

### 4.5 เอกสารประกอบการใช้งาน

เอกสารอธิบาย

- การติดตั้งหรือการวาง folder
- วิธีใช้งาน
- วิธีตรวจสอบผลลัพธ์
- วิธีดู log
- แนวทางแก้ไขปัญหาเบื้องต้น

---

## 5. ขั้นตอนการดำเนินงานโดยสังเขป

แนวทางการทำงานของโครงการนี้โดยสรุปมีดังนี้

1. รับ requirement และทบทวน workflow ปัจจุบัน
2. รับ sample PDF จริงจากลูกค้าเพื่อนำมาวิเคราะห์
3. ตรวจสอบ metadata ที่มีอยู่จริงใน report แต่ละประเภท
4. ออกแบบ logic สำหรับ comparison, naming, grouping, merge และ delivery
5. พัฒนาโปรแกรมหรือ utility ตามขอบเขตที่ตกลง
6. ทดสอบกับไฟล์ตัวอย่างและกรณีสำคัญ เช่น same-day multi-case
7. ปรับแก้ตามผลการทดสอบ
8. ส่งมอบระบบ พร้อมเอกสารประกอบและ handover

---

## 6. เงื่อนไขและข้อสมมติฐานสำคัญ

ขอบเขตงานฉบับนี้ตั้งอยู่บนข้อสมมติฐานดังต่อไปนี้

- ลูกค้าสามารถจัดเตรียม sample PDF จริงให้วิเคราะห์ได้
- PDF ที่ใช้งานสามารถอ่านข้อความได้ในระดับที่เหมาะสม
- มีการกำหนด source folder และ destination folder ได้ชัดเจน
- ระบบจะทำงานในสภาพแวดล้อม Windows
- มีเครื่องหรือ environment สำหรับรันงานแบบ scheduled processing
- รูปแบบ report จากต้นทางมีความเสถียรในระดับที่นำมาพัฒนา logic ได้

หากภายหลังพบว่า PDF บางส่วนเป็นภาพล้วนหรือ metadata ไม่สม่ำเสมอ อาจต้องมีการขยาย scope เพิ่มเติม

---

## 7. สิ่งที่อยู่นอกขอบเขต (Out of Scope)

รายการต่อไปนี้ถือว่าอยู่นอกขอบเขตของเอกสารฉบับนี้ เว้นแต่จะมีการตกลงเพิ่มเติมเป็นลายลักษณ์อักษร

- การเชื่อมต่อ `API` โดยตรงกับ `EPHIS`
- การเชื่อมต่อ database โดยตรงกับ `Innovian`
- การทำ `OCR` สำหรับ PDF ที่เป็นภาพล้วนหรือคุณภาพต่ำ
- การพัฒนา workflow อื่นที่ไม่เกี่ยวข้องกับ PDF management นี้
- การ deploy แบบ multi-site ที่มี rule ต่างกันหลายโรงพยาบาล
- การ support แบบ 24/7
- งานด้าน infrastructure ของโรงพยาบาลที่ไม่เกี่ยวข้องกับ scope นี้

---

## 8. จุดที่ต้องยืนยันก่อนสรุป final scope / quotation

ก่อนสรุปราคาและแผนงานอย่างเป็นทางการ ควรยืนยันข้อมูลต่อไปนี้ร่วมกัน

- มี report กี่ประเภทที่ต้องรองรับ
- ในแต่ละ report มี field อะไรที่ใช้ได้จริงบ้าง
- encounter key ที่ปลอดภัยที่สุดคืออะไร
- ปลายทางต้องการไฟล์แบบแยกราย report หรือ merged per encounter
- schedule การประมวลผลต้องการให้เริ่มเวลาใด
- destination workflow ต้องการเพียง folder handoff หรือมีขั้นตอนเพิ่มเติม
- กรณี ambiguous case ต้องการให้ระบบ block, skip หรือให้ review อย่างไร

---

## 9. เกณฑ์การรับมอบงานเบื้องต้น

เกณฑ์การรับมอบงานในเบื้องต้นควรพิจารณาจากหัวข้อดังนี้

- โปรแกรมสามารถอ่านไฟล์ PDF จาก source folder ได้
- สามารถดึง metadata สำคัญจาก sample file ที่ตกลงร่วมกันได้
- สามารถเปลี่ยนชื่อไฟล์ตาม format ที่อนุมัติได้
- สามารถจัดกลุ่มหรือ merge PDF ตาม logic ที่ตกลงได้
- สามารถส่งไฟล์ไปยัง destination folder ได้
- มี log สำหรับตรวจสอบผลการทำงาน
- มีเอกสารประกอบการใช้งานและ handover เบื้องต้น

---

## 10. ข้อเสนอสำหรับขั้นตอนถัดไป

ขั้นตอนถัดไปที่แนะนำคือ

1. ส่ง sample PDF จริงจากลูกค้าเพื่อวิเคราะห์
2. ยืนยันประเภท report และ metadata ที่มีอยู่จริง
3. ยืนยัน naming format และ destination workflow
4. สรุป final scope และจัดทำ quotation

หลังจากนั้นจึงเข้าสู่ขั้นตอน development ตามแผนงานที่ตกลงร่วมกัน
